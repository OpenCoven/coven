# Returning-device endpoint transport

Source-adjacent implementation notes for #787 / #1527. The outbound relay client, daemon relay workers and operator configuration commands shipped in #1551. Rendezvous recovery beyond the current slot (#1526), complete client UX and an independent human security review remain open under #787. Passing local controlled-broker and real-router fixtures is not NAT/mobile acceptance.

## Cryptographic and authority boundary

The device initiates `Noise_NK_25519_ChaChaPoly_SHA256` against a pairing-scoped responder key authenticated by the existing pinned P-256 installation identity. NK messages have empty payloads; no application request or stable device identity is sent before the channel exists. Each connection generates fresh ephemeral keys and challenges. The relay credential authorizes room routing only.

The fixed-array deterministic CBOR Noise-key binding is `["coven.mobile.noise-binding", 1, profile, device_uuid_bytes, grant_uuid_bytes, revocation_epoch, host_uncompressed_sec1_bytes, device_uncompressed_sec1_bytes, noise_public_bytes]`. UUIDs are 16-byte byte strings, keys are byte strings, and epoch is an unsigned integer. The signature is a fixed 64-byte P-256 ECDSA signature over the complete CBOR bytes. The client verifies against its existing host/device pins, never keys merely supplied by discovery or a broker.

The public Noise prologue is `["coven.mobile.connection", 1, profile, transport, context]`, where transport is `"relay"` or `"direct"` and context is a 32-byte opaque room/direct context. It contains no stable identity. The possession proof is `["coven.mobile.possession", 1, profile, role, handshake_hash, host_nonce, device_nonce, device_uuid_bytes, grant_uuid_bytes, revocation_epoch, host_uncompressed_sec1_bytes, device_uncompressed_sec1_bytes, noise_public_bytes]`. The role is `"host"` or `"device"`; the final Noise handshake hash and both 32-byte fresh challenges are byte strings. Proof encodings are generated locally from trusted context, not decoded from an unbounded peer-controlled CBOR graph.

Inside the Noise channel, the host sends its nonce, the device sends its nonce, the host sends its signature, and only after verifying that signature does the device send its own signature. Host and device completion records are `host-finished-v1` and `device-finished-v1`. The entire handshake/proof exchange has one absolute 30-second budget. The host checks current policy before handshake, after possession proof and after completion. No early application data or bearer resumption is implemented.

`authority::check_current` reloads durable registry state and checks device key, suspension/revocation, grant ID/epoch, validity and direct-only restrictions. This is channel admission, not a user-verification claim. `gateway::serve_authenticated_transport` retains the existing per-request signature, assurance, nonce/rate and post-response checks, shares their state with direct HTTPS, and requires the request's device ID to equal the channel identity. Unprotected routes, trailing requests and query-string targets are rejected; like direct ingress, which answers a query-string target with 404, the transport refuses `?` before routing or signature verification instead of stripping it (#1610), so no route runs and the request nonce is not spent. Errors close the channel; device deletion closes it after returning the authenticated operation result. A current grant must match the channel's grant ID and revocation epoch before and after every request, so a grant rotation or revocation closes the channel at the next request rather than at the next reconnect, and the manager's one-second policy reload cancels an idle worker whose grant is no longer current.

### Idle policy and keepalive (#1609)

The relay worker waits for the next request on an authenticated channel without a request deadline; an idle channel is not torn down and the peer does not re-authenticate while it stays reachable. The wait is bounded by liveness, not time:

- After 30 seconds without an inbound frame (`websocket::KEEPALIVE_INTERVAL`) the host sends a WebSocket ping. `coven-relay` answers pings itself, never forwards them, and resets its 120-second idle timer on every inbound frame, so the cadence holds the host's socket with a four-ping margin.
- A frame must arrive within 10 seconds of a ping (`websocket::KEEPALIVE_BUDGET`) or the path is dead: the wait fails with `relay peer unresponsive`, the channel closes and the worker reconnects with its normal backoff. A dead or black-holed relay connection is therefore detected within 40 seconds.
- A device that leaves is reported by the relay with a close frame (`1001 relay peer disconnected`), which fails the wait at once. A device whose socket died silently is dropped by the relay's own 120-second idle timer and then reported the same way, so a dead device is detected within about 130 seconds. Devices keep their own relay socket alive by sending frames; the host does not send application-level keepalives on the device's behalf.
- Cancellation from the manager (configuration or trust change, disable, host-identity change, failed current policy, daemon stop) interrupts the idle wait exactly like a bounded read, so the daemon's two-second stop budget holds with an idle channel.
- Once the first record of a request arrives, the remaining fragments and the response are bounded by the 15-second `MOBILE_IO_TIMEOUT`, the same mid-request budget as direct HTTPS. A peer that starts a request and stalls cannot hold the channel.

The idle wait is the transport's `Records::receive_idle`; the fixed-deadline `receive` used during the handshake, proofs and mid-request I/O is unchanged. A stalling broker that keeps answering pings holds an idle channel open, but it cannot use it: every request still needs the device's per-request signature, and a withheld record is unusable once the device's own deadline has failed its channel.

## Records and messages

WebSocket messages and frames are bounded at 65,535 bytes. Noise plaintext is bounded at 65,519 bytes. WSS validates the configured host certificate, uses one HTTP upgrade without redirect following, and carries only binary application records plus the idle keepalive's empty ping/pong control frames. Absolute read/write deadlines are refreshed against the same deadline before each underlying socket operation; the idle wait slices its reads at the keepalive interval and a partial frame buffered across a slice is resumed on the next read. DNS resolution remains the connection scheduler's responsibility. Unknown dependency loggers cause WSS startup to fail closed; the CLI-owned legacy logging filter excludes dependency targets because Tungstenite trace events can contain serialized credentials.

A logical message starts with an encrypted record containing byte `1`, a four-byte big-endian total length, and up to 65,514 payload bytes. Further encrypted records contain byte `2` and up to 65,518 payload bytes. Every fragment must have exactly the expected length; empty continuations, surplus/truncated fragments and messages over the caller's limit fail closed. Allocation happens only after validating the total. Noise ordering/authentication protects the sequence, and a failed record or message cannot be reused with the same channel state.

Each cancellable WSS attempt has a one-shot token. Socket registration and cancellation share a lock, so cancellation before registration closes a late socket, and cancellation after registration shuts down both socket directions to interrupt TLS, upgrade and record I/O. TCP establishment uses the workspace's existing Mio poller in nonblocking mode with a cancellation waker and the caller's absolute deadline; it does not shorten the network deadline to make shutdown fast. Dropping the attempt releases the cloned cancellation socket; finished and cancelled tokens cannot start another connection.

Endpoint resolution bypasses DNS for literal IPv4/IPv6 addresses. Hostname resolution admits at most four outstanding system resolver calls process-wide and returns at most sixteen candidate addresses. Cancelled or timed-out callers stop waiting, but their slots remain occupied until the underlying resolver returns; retries or daemon restarts cannot create an unbounded set of abandoned resolver threads. A saturated resolver reports a connection failure without changing authorization. DNS and TCP wait slices are capped at 50 ms, with a TCP waker for cancellation notification; observed scheduling latency is not guaranteed by those configured intervals. The Unix child-process fixture covers shutdown with an authenticated idle relay connection and during an unfinished TLS handshake; pending-resolver process shutdown and Windows lifecycle evidence remain separate. System resolver calls themselves are not forcibly terminated.

## Secret-memory limits (#1611)

CLI-owned `Material.noise_private`, the routing seed and credential, private-file read buffers, and received plaintext/reassembly buffers use `Zeroizing`; `StoredMaterial` and `Provisioning` derive `Zeroize` and `ZeroizeOnDrop`. These protections wipe their own buffers on normal drop. They do not erase copies made before wrapping, during serialization, or inside dependencies, and do not guarantee erasure after a process crash or from swap, core dumps or other system copies. The private transport files intentionally retain pairing keys and routing seeds for restart.

The locked `snow 0.10.0` implementation does not zeroize `HandshakeState`/`TransportState` secret material on drop. Its default resolver stores the copied Noise static key, ephemeral X25519 private keys and ChaCha keys in ordinary arrays; handshake chaining keys and temporary derivation buffers also lack zeroization. Dropping or closing a channel, including after cancellation, timeout or malformed input, invalidates its use but does not guarantee that these dependency-owned copies are wiped from freed memory. Zeroizing the CLI's original private-key buffer does not wipe Snow's copies. This dependency limitation is tracked upstream in [mcginty/snow#203](https://github.com/mcginty/snow/issues/203); no upstream fix is adopted by the current lockfile.

Bootstrap provisioning is **not serialized through zeroizing buffers end to end**. In `gateway.rs`, `TransportBootstrap` converts `Provisioning` through `json_value` into an ordinary `serde_json::Value`; `success_response` serializes the envelope into `MobileHttpResponse.body: String`; `MobileHttpResponse::to_http()` formats another plaintext HTTP response and returns its ordinary `Vec<u8>`. V2 prepare/recover responses also pass `storage::v2::Handover`, which contains a routing seed and derives `ZeroizeOnDrop`, through the same `json_value` and HTTP response path. These representations contain routing seeds and are not zeroized on drop, even though the original `Provisioning` or `Handover` fields are. Both pinned HTTPS and authenticated Noise response paths use these buffers; encryption in transit does not erase the plaintext serialization copies in process memory.

Cancellation and timeout cleanup therefore provide bounded resource release and channel invalidation, together with zeroization of the CLI-owned buffers described above, rather than erasure of every secret copy. Keep provisioning inside authenticated TLS/E2EE and out of logs; do not treat these memory protections as a guarantee against process-memory disclosure.

## Provisioning and persistence

`POST /api/v1/mobile/transport/bootstrap` uses the existing signed-request and current-grant/assurance path. It returns transport material for that authenticated device only. It does not enroll a new device or issue a broader grant. Relay endpoints and their CA certificates are attached only when the relay admission check (`authority::check_current` with `direct = false`) would admit the grant; a `DirectOnly` grant still bootstraps over the direct channel but receives an empty `relayEndpoints` list (#1614). A previously enrolled client first upgrades over its existing pinned HTTPS connection; no new QR is needed. Endpoint/client proof remains mandatory on every subsequent connection.

`coven doctor` reports live direct and relay connection observations, or unavailable when the daemon cannot supply them. JSON exposes only `state` and `transport` in `mobileDirectConnection` and `mobileRelayConnection`, or null. An online channel never authorizes an operation or clears suspended/revoked/expired/rotated state. Unix probes use private socket discovery; Windows probes retain owner-only pipe discovery and negotiated daemon-instance binding. Each probe has a 500 ms caller budget. `coven memory mobile status` and `coven memory mobile relay status` continue to report configuration only. No diagnostic includes a URL, room, credential, key or device identifier.

`mobile/relay.json` is an optional private version-1 configuration with `enabled` and up to four explicit WSS `/ws` endpoints. Absence disables relay access. No endpoint is built in. Userinfo, queries, fragments, invalid versions and malformed/insecure state fail closed. Enabled configuration starts daemon-owned outbound workers; enabling it on an already-running daemon still requires restart.

`coven memory mobile relay reset --yes` explicitly confirms replacement of relay configuration with version 1, `enabled: false`, and an empty endpoint list. It does not decode existing configuration, so corrupt JSON, oversized files and unsupported versions can be recovered. Reset shares the incremental-update process/file lock and private atomic replacement checks; symlinks, non-regular files and unsafe permissions remain rejected. It never opens or changes host identity, paired-device keys, grants, pairwise transport material or direct gateway configuration. Without `--yes`, reset fails before accessing the configuration. Load errors name the confirmed recovery command. JSON parse errors retain only category and line/column; saved field names and values are omitted. Running relay workers observe the disabled configuration through their existing reload path.

Each endpoint is an object with `url` and optional `caCertificates`. An empty certificate list uses the normal WebPKI roots. A nonempty list explicitly replaces that root set for this endpoint only and still validates the URL hostname. Certificates are canonical unpadded base64url DER, bounded to four certificates of at most 8 KiB each; the complete stored configuration must fit the existing 16 KiB private-state limit. Unknown fields, malformed certificates and duplicate normalized endpoint URLs fail closed. The authenticated bootstrap carries these settings to the enrolled peer without changing pinned endpoint identities or routing material. There is no insecure TLS switch or trust learned from a relay response.

Operator commands configure explicit endpoints without enrolling a device or selecting a hosted service:

```sh
coven memory mobile relay add --endpoint wss://relay.example.test/ws
coven memory mobile relay add --endpoint wss://private-relay.example.test/ws --ca-certificate /path/to/ca.pem
coven memory mobile relay enable
coven memory mobile relay status --json
coven memory mobile relay disable
coven memory mobile relay remove --endpoint wss://relay.example.test/ws
```

New configuration starts disabled. `add` updates one normalized endpoint while preserving current enablement; `--ca-certificate` accepts bounded PEM certificate files and applies only to that endpoint. The certificate bytes are stored, so editing the original PEM later does not silently change trust. `enable` requires the existing host identity and never creates one. Removing the last endpoint disables relay access. Incremental commands use a shared process/file lock and atomic private-file replacement; rejected input leaves the prior configuration unchanged. Status reports configuration counts and enablement, not live connectivity or broker URLs.

Each device's private `transport-<uuid>.json` stores its grant binding, Noise keypair and independent random routing seed. File ownership/mode checks, bounded reads, a process/file lock and atomic replacement protect persistence. The seed/keypair survive restarts. A changed grant ID/epoch or identity invalidates the previous binding and generates fresh transport material only after current authority checks. Private keys never enter the bootstrap response. Routing material in the response must remain inside authenticated TLS/E2EE and out of logs.

Room and routing credential are derived using HKDF-SHA256: salt `coven.mobile.rendezvous.v1`, input key material the pairwise random seed, and info concatenating transport (`direct` or `relay`), purpose (`room` or `credential`) and the eight-byte big-endian slot. Output length is 32 bytes. Slots are 600 seconds. Independent seeds and domain separation separate devices, grant generations, direct/relay paths and time slots. This derivation does not by itself implement consumed-room tracking, bounded skew/restart recovery or the connection scheduler; those remain required before seamless-reconnect acceptance.

## Daemon ownership and remaining scheduling work

The daemon can start relay access with the private HTTPS listener disabled or its configuration file absent, using the existing enrolled host identity. Relay-only startup reads that identity without creating keys, changing its LAN certificate or resolving the old LAN endpoint. When HTTPS is enabled, both transports share the exact same authority/authenticator state. Workers only read previously provisioned device material; network availability never creates an enrollment or changes a grant.

A manager admits at most 32 peer workers, rotates candidate ordering for capacity fairness, uses bounded exponential retry delays with jitter, and rotates among configured relay endpoints on failures. It reloads private relay configuration and current authority every second. Disable, endpoint/trust changes, host-identity changes, and failed current policy cancel affected workers. The disable command also disables relay access; status reports configuration separately for the listener and relay without claiming a live connection. Worker and manager ownership cancels active DNS/TCP/TLS/record waits and joins workers on shutdown. The real-router runtime test covers relay-only signed requests, restart with unchanged pairing material, idle-worker stop under the documented two-second budget, live disable, and revocation; a second runtime test holds an authenticated channel idle for longer than the former 15-second request deadline, then completes a signed request on the same Noise session with no further host upgrade in the relay's capture, and stops the runtime inside two seconds while the channel is idle; a Unix child-process fixture also runs the production daemon loop, completes a signed request through the real relay, invokes the production stop API while the connection is idle, enforces its two-second budget, and requires graceful child exit. A second process case receives a TLS handshake record and withholds the response, requiring the same bounded graceful shutdown during the unfinished handshake. This does not establish Windows lifecycle behavior or real mobile/network acceptance.

This paragraph describes v1 workers, which serve pairings that have not completed a v2 handover; v2 counter rooms are described under the #1645 section below. V1 workers rendezvous only in the current 600-second slot of the host clock. A device whose clock is in a different slot, or that is still using a previous slot's room, is never paired: the relay closes its first forward with code 1013 and the device must rejoin the room of the current slot, which needs no re-enrollment or new material. Reconnects within one slot reuse the same room and credential. There is no clock-skew window, consumed-room tracking or prolonged-offline recovery policy; those are the routing review in #1526. Do not infer seamless reconnection across those cases from the runtime tests.

The daemon-owned mobile runtime now lives in a contained Rust child process. The same native gateway owns direct HTTPS/WSS, relay workers and authority state there; the daemon proxies existing owner controls only after its existing owner and chat-context gates. A private inherited-pipe handshake verifies the protocol and source stamp before settings, profile-lock or native startup effects. The source stamp is a compatibility check, not binary attestation. The parent bounds the handshake to 1.6 seconds; native startup shares one one-second lock-admission deadline across initial stores. Startup waits observe daemon termination during Hello/Ready and carry the first observed stop deadline into cleanup. Startup failure retains checked cleanup ownership rather than silently disabling a valid enabled configuration.

Native startup, owner controls and every native authority worker enter a runtime-owned storage cancellation scope. Registry, authorization-key, assurance-challenge, introduction, policy, passkey, audit and provisioning lock waits observe cancellation. The stopped scope refuses further admission; unrelated standalone transactions and newly loaded stores retain their own scope. Cancellation of a wait does not interrupt an already entered synchronous filesystem call. Deterministic contention tests synchronize on a real failed acquisition, hold competing locks through observed shutdown and verify unchanged authority bytes.

Daemon shutdown closes mobile admission before waiting on other subsystems. Mobile cleanup receives one absolute deadline measured before session, scheduler and TCP cleanup, rather than a renewed budget at the tail. The child observes Stop independently of its authority thread. Cooperative cleanup gets a bounded grace period; a strict process-tree backstop contains work held inside storage I/O. Successful cleanup requires observed child exit, reaping and joined parent pipe workers. If that cannot be established, the daemon retains the child/tree, pipe workers, profile lease, serving lock and socket/status ownership while the existing stop controller reports failure. A panic hook cannot clear those paths ahead of the serving owner's cleanup. No detached authority work or fabricated stopped state is accepted.

On Windows, the daemon advertises the `observed-workers-v1` lifecycle contract. The stop client retains the authenticated root process HANDLE, verifies a new owner-validated shutdown pipe against the same PID and creation time, requires the exact contract in the identity-bound acknowledgement, and waits within its original deadline. A timeout, malformed response, identity change or required-contract refusal cannot fall back to root termination. Legacy termination requires both an absent contract advertisement and an authenticated explicit 404/405 response from the older peer.

An interrupted admitted mutation can have an unknown outcome. Pending owner controls return existing `daemon_unavailable` 503 with `outcome: unknown` and `retrySafe: false`; uncertain remote pairing uses the existing code with `retryable: false`. Reconcile current enrolled-device/grant state before deciding whether to start another operation. Initial enrollment uses a durable intent to reconcile the device/key stores by exact recognized before/after images; conflicting or corrupt images fail closed without overwriting unrelated authority. Create-only files publish complete staged bytes without replacing an existing name. Coarse audit appends recover an unfinished final suffix while preserving complete earlier evidence. A write that crossed publication may remain committed; unchanged-byte assertions apply to cancelled admission or the tested pre-publication cuts, not every interrupted transaction.

Local qualification uses actual native children, encrypted relay requests, same-profile restart, strict stop assertions, real process exit/reap and synthetic held-write or injected-error checkpoints. The retained-owner test withholds observation without fabricating exit or kill success, then resumes actual observation before cleanup. These fixtures do not establish physical disk stalls, power-loss durability, native Windows lifecycle acceptance, physical mobile/network acceptance or independent security review. Generic mobile filesystem barriers retain their existing platform behavior; the separate v2/restore checked durability requirements remain unchanged.

## Verification boundary

`vectors/wire.json` pins the current draft's signed binding/proof preimages, direct/relay prologues, and routing derivation outputs. Regenerate or check it with `python3 crates/coven-cli/src/mobile_memory/transport/vectors/generate.py --write` or `--check`. The generator uses a separate fixed-type encoder following [RFC 8949](https://www.rfc-editor.org/rfc/rfc8949.html), standard-library HMAC/SHA-256 following [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869.html), and OpenSSL-derived public points for synthetic scalars 1 and 2. No private key file or new package is needed. Rust tests compare exact bytes across unsigned-integer encoding boundaries through `u64::MAX`, both proof roles, both transports and multiple routing slots. These are reproducible encoding/derivation review fixtures, not independent signature/Noise interoperability, a frozen protocol or security approval.

The real relay registers peers after the HTTP upgrade, has no peer-ready notification, and closes an attempted forward with code 1013 when the opposite role is absent. An upgrade response therefore does not establish peer readiness. The outbound scheduler must tolerate this race with bounded reconnect/backoff and fresh Noise state; a fixed sleep before sending is not a correctness mechanism. The server deletes a room after both peers leave and does not persist consumed-room history, so any single-use policy must be enforced by the endpoints. These constraints must be covered by real-server acceptance before daemon wiring is enabled.

The controlled TCP/WebSocket broker fixture exercises normal encrypted exchange and tamper, replay, drop, oversized record, reflection, truncation, injected record, reordered handshake, plaintext-fallback and stalled-record attacks. Negative cases require both endpoints to reject the exchange before authenticated admission; the positive control requires both to admit and exchange the exact application payloads. The reorder case swaps two actual consecutive host records without a timing sleep. The stall case forwards the whole authentication exchange, then withholds the first application record with both sockets open: each endpoint fails at the fixed deadline it passed, the failed channel stays closed, and the late record is unusable. Keepalive cases run the idle wait against a plain-WebSocket broker with a shortened interval: a broker that answers pings sees three probes before it releases the record, a broker that holds the TCP connection open without answering fails the wait as `relay peer unresponsive` after one interval plus one budget, and cancellation interrupts the idle wait inside the two-second stop budget; the production router case holds an idle authenticated channel across three pongs visible in the relay's capture and then delivers the late record on the same session. A substitute-peer case uses the production router: a host with a different pairing-scoped Noise key fails the device's NK handshake, and a device with the copied binding but a different signing key fails the host's proof check; neither side reaches admission. Every captured frame, and the fixture relay's complete TLS-terminated byte stream including the HTTP upgrade, is checked for the application plaintext, the completion records, the device and grant UUIDs (raw and text), the host and device P-256 points (uncompressed, compressed and x coordinate) and the pairing-scoped Noise static key. Only the rotating room identifier and credential are visible to the relay. Absence of these markers is necessary evidence, not a confidentiality proof. The real-router fixture hosts the same router as the relay executable behind a local TLS listener, then exercises the production WSS connector, explicit certificate trust, two fresh Noise sessions with unchanged pairing keys, and fragmented request/response delivery. A ping/pong barrier synchronizes fixture registration without timing sleeps; it grants no endpoint trust. Separate TLS tests reject unknown roots and wrong hostnames before application bytes and reject malformed trust configuration. These are in-process local tests, not independent deployment or NAT/mobile evidence.

Registry tests exercise suspension, revocation, expiry and direct-only admission. Provisioning tests exercise restart stability, rotating routing, pin mismatch and grant changes. Gateway tests exercise shared request replay state, channel/request identity binding, query-string rejection (a signed `DELETE /api/v1/mobile/device?…` leaves the device unrevoked, the rejected request never reaches the verifier, and later requests keep replay semantics), endpoint/trust updates without changing paired identities or routing material, and `DirectOnly` bootstrap: the direct-channel response carries no relay URL or CA DER, a relay-channel bootstrap is refused, and the production relay runtime refuses the device until a re-provisioned unrestricted grant connects on the same runtime as a positive control. A second runtime test drives two persistent synthetic peers through the production router: previous- and next-slot attempts fail within bounds and leave the registry bytes unchanged, the current slot connects, a signed query-string request closes the live session without a response while the same material reconnects, a grant rotation fails the live session and the stale material while re-provisioned material connects, a daemon restart reconnects with unchanged identity and material, and a revocation fails the live session and reconnection. Pending-connect and Windows daemon lifecycle, no-QR client journeys, LAN/migration, independent cross-implementation vectors and an independent human security review remain separate required evidence.

## V2 routing implementation (#1645)

The isolated #1645 implementation adds `routing.rs` for length-prefixed v2 HKDF and checked host/device counter transitions, `routing/channel.rs` for versioned possession and persistence ordering, and independent fixtures. The relay runtime listens on v2 counter rooms (`gateway/relay_runtime/counter.rs`) for pairings with v2 state. It keeps v1 workers only for pairings that have not completed an authenticated v2 handover, and v1 material is refused once a pairing's v2 protocol floor exists. Passing these primitive/channel tests is not v2 daemon acceptance.

The v2 possession array is `["coven.mobile.possession", 2, profile, role, handshake_hash, host_nonce, device_nonce, device_uuid_bytes, grant_uuid_bytes, revocation_epoch, host_uncompressed_sec1_bytes, device_uncompressed_sec1_bytes, noise_public_bytes, g, c, k]`. Its host record inside Noise is exactly `u64be(g) || u64be(c) || u64be(k) || signature64`; the device verifies the signature over the complete deterministic-CBOR array before interpreting the tuple as authenticated routing state. The device response is its signature over the same fields with role `device`. Completion records are `host-finished-v2` and `device-finished-v2`. Neither completion changes routing counters. V1 binding/prologue bytes and fixtures remain unchanged.

### Independent fixture provenance and limits

`vectors/generate-v2.py` uses standard-library HMAC/SHA256, an independent RFC 8949 CBOR encoder and synthetic OpenSSL public keys. `wire-v2.json` carries separate fixture-format, routing-protocol and possession-proof version fields. It covers both transports and generation/counter encodings 0, 1, 2^32 and u64::MAX. The original `wire.json` and generator remain byte-identical.

`vectors/generate-channel-v2.mjs` uses Node/OpenSSL P-256, X25519, SHA256/HMAC and ChaCha20-Poly1305 independently of Rust/ring/snow. `channel-v2.json` contains positive signatures, corrupted signatures and wrong-role preimages, plus complete direct/relay two-message NK transcripts, handshake hashes and bidirectional first transport records. ECDSA signatures are generated once and retained; `--check` independently verifies the retained signatures and regenerates deterministic transcript bytes. Synthetic private inputs are fixtures only. This evidence establishes interoperability for the enumerated bytes, not independent cryptographic review, crash durability, real-device behavior or hosted acceptance.

The accepted arithmetic also reaches an availability edge: three dropped device proofs followed by a fourth committed attempt leave `c=4,d=4,f=0`; the pre-connect check refuses the next remote attempt. Production-channel/file tests reproduce this both with the host completion dropped and with both completions and bidirectional encrypted records delivered successfully, because neither completion changes `f`. On 2026-11-06 the owner accepted this as a direct-recovery availability limit ([#1526](https://github.com/OpenCoven/coven/issues/1526#issuecomment-6688535435)): the device needs an authenticated direct `max(c, d)` resync. The implementation preserves the frozen equations and does not enlarge the window or claim broader lost-completion availability.

### Durable v2 state and signed direct control (implementation candidate)

`storage/v2.rs` keeps committed/pending generations and both transport floors in the original per-device material path. Before any v2 material is published, a private, synced `.transport-v2-<device>.required` marker establishes a persistent protocol floor. The legacy loader/provisioner refuses while that marker exists, including when the material file is missing or corrupt. The v2 writer performs private temporary replacement with file and directory synchronization, then checked retained-directory barriers through the shared native durability implementation (including NTFS enforcement on Windows). Every error is uncertain; callers abort before the next protocol message and re-read retained state on retry.

The host serializes consuming writes through `.transport.lock`, reloads generation/floor and current registry/grant, rejects stale room/generation/key/grant snapshots, and saves the new floor before completion. Device `Attempt` holds its OS transport lock from before joining through proof/completion, persists both next room and authenticated floor before its proof, and cannot be reused after success or error. Same-value handover retries preserve already-consumed device and host counters; they never reset a committed generation.

V2 control uses the existing signed `POST /api/v1/mobile/transport/bootstrap` path over pinned authenticated direct ingress. The enclosing HTTP/mobile request protocol remains version 1; the routing body has its own `version: 2`. Nonempty control bodies have an exact operation schema and unknown fields/versions are refused. Rust's ingress dispatcher, rather than a request field/header, decides whether the path is direct. Relay ingress refuses all v2 control operations with 403. An empty legacy bootstrap request cannot reopen v1 after the protocol floor is established.

| Operation | Routing request fields beyond `version: 2` | Durable result before success |
| --- | --- | --- |
| `prepare` | `operation: "prepare"` | Persist one pending generation/seed; same-authority retries return the same value; no listener activates before acknowledgment |
| `acknowledge` | `operation: "acknowledge"`, `generation`, `seedDigest` (32-byte SHA256 digest as a JSON byte array) | Commit only the exact pending value; equal committed acknowledgment retries repeat barriers without resetting counters |
| `resync` | `operation: "resync"`, `transport`, `generation`, `next` | Host stores `c=max(c,d)` and returns generation/floor; device durably stores `d=f=c` after authenticating the direct response |
| `recover` | `operation: "recover"`, optional `knownGeneration` | Explicitly repair missing/corrupt private host state with a `g+1` handover anchored in retained host or authenticated device generation; no generation is guessed when both anchors are missing |

A re-grant, key change or epoch change invalidates pending old authority. That pending generation is burned; a replacement advances beyond the highest offered generation and never replaces a seed at the same generation. A device may skip a generation burned before it adopted it, but only on a strictly increasing authenticated direct handover. Stable-authority retries still require identical pending cryptographic material. The owner accepted this treatment on 2026-11-06 ([#1526](https://github.com/OpenCoven/coven/issues/1526#issuecomment-6688535435)).

The v2 device-side handover verifier authenticates the unchanged Noise-key certificate against existing pins. Seed/generation authenticity comes from the pinned authenticated direct ingress; the unchanged certificate does not independently sign those fields. Corrupt device state is replaced only through explicit direct recovery adoption. Counter/generation overflow is refused; generation overflow requires re-pairing. Snapshot restore remains outside the guarantee unless the explicit operator ceremony is used; complete restore acceptance remains unproven pending the remaining process, power-loss and device cases, tracked in #1679, #1680, #1681 and #1682.

Current evidence includes native encrypted exchange with both actual files, signed direct control dispatch, independent-process consumption races, and injected post-rename directory-sync failures whose retained state is re-read before retry. Those failures do not imply rollback: a counter/generation may already be committed even though no success is returned. Native host-worker integration exercises v2 rooms across real relay endpoints and the shared installation budget. Real power-loss models (#1679), complete restored-snapshot and operator-ceremony acceptance (#1680, #1681) and device acceptance (#1682) remain open in follow-up issues. The measured W=4 edge is an accepted availability limit (#1526).

The Rust transport surface exposes `routing::channel` and `storage::v2` alongside the existing v1 helpers. ## Authenticated migration

The existing operator-enabled private TLS gateway also accepts direct WSS upgrades at `/ws`, using the same bounded WebSocket record codec, TLS 1.3, pinned provisioned trust, Noise profile and endpoint proofs as relay connections. No additional listener or built-in endpoint is created. The routing query uses version 1, an opaque direct-domain room and client role; the independent bearer routing credential remains inside TLS. Routing only selects a currently active provisioned pairing. Wrong/duplicate query fields, wrong role, stale/wrong room or credential, and unavailable policy fail closed before application traffic. A direct upgrade scans the bounded registry (at most 128 devices), including provisioned pairings after earlier unprovisioned records. V2 pairings use only the accepted W = 4 counter window, with locked proof refresh and verified consumption; legacy slots apply only to pairings that have never adopted v2. Missing, malformed or fenced v2 state fails closed. The HTTP relay wire query remains version 1; endpoint v2 possession and durable generation/counter authority are enforced inside Noise. Current authority is checked again during Noise and for every signed operation. Discovery and automatic LAN candidate selection remain owned by #1529.

`migration::Migration` retains one pinned pairing and signs each `PendingOperation` once. Its nonce is the operation identity. Network changes and uncertain outcomes leave those exact signed bytes untouched; they never renew a timestamp, mint a new operation identity, re-enroll or change a grant. A candidate performs a new handshake outside the handoff lock, so old work may continue. Only the latest candidate from that migration controller can be committed. A successful commit replaces the selected channel while old in-flight work can finish; a late old-channel failure cannot mark the replacement offline. A failed candidate leaves the old channel selected. Requests from another controller/pairing cannot be submitted implicitly.

An exchange error is an uncertain outcome. Keep the original operation and reconcile its effect before deciding what to do next. A replay rejection is not evidence that the original operation had no effect. There are no automatic application retries, resumption handles or early application data. Replay state is shared by direct and relay ingress within the daemon; crash/restart outcome reconciliation and persistent client queues are not claimed by this interface. The accepted v2 routing construction landed in #1677 and is reused unchanged: a candidate calls `routed` with its existing private device store, obtains that one-shot attempt's room and credential, then authenticates through the production durable counter helper. The stored host/device/grant/Noise pins must match the migration controller before joining; no callback supplied by the caller can bypass durable consumption. The device lock lasts through authentication and is released before the channel becomes the live selection. No legacy fallback is attempted for an upgraded pairing.

Direct and relay attempts retain bounded I/O and cancellation. Shutdown first refuses new accepted sockets and cancels registered I/O, then reaps owned connection threads. Excess connections are refused rather than being served synchronously on the listener. Local E2E fixtures cover response loss after a durable challenge effect, overlapping relay handoff with the same signed operation and one effect, relay/direct/relay transition under traffic, unchanged authority, fresh Noise ephemeral keys, and real daemon phase observations. These are controlled local network fixtures; physical Wi-Fi/cellular switching, NAT/mobile acceptance and independent security review remain separate evidence.

The current v2 migration fixture uses production relay counter workers and direct WSS ingress on the same authority/authenticator state. It consumes independent direct/relay counters across relay/direct/relay handoff, keeps an older channel usable until commit, rejects stale controller pins, retries one immutable signed challenge operation without another durable effect, checks coarse online/offline observations and preserves device/grant authority. These checks do not replace physical-network, native Windows, independent review or protected delivery evidence.
