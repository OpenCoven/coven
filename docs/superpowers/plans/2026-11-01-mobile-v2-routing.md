# Mobile v2 routing implementation plan

**Goal:** Complete #1645, including every requirement carried from #1644, against the accepted #1526 contract at d151b653.

**Architecture:** Rust owns generation and counter persistence, authenticated consumption, recovery and listener admission. The existing Noise NK and P-256 identity binding remain; a separate versioned possession transcript binds routing state. Existing v1 material upgrades only through authenticated direct handover and cannot downgrade.

**Tech stack:** Existing Rust, ring HKDF, snow, P-256, private atomic files and fs2 locks; independent Python/OpenSSL fixture generation.

**Spec:** `docs/architecture/mobile-device-reconnect-contract.md`, especially “v2 routing (accepted 2026-10-30)”; canonical GitHub issue #1645 retains #1644's complete matrix. This is execution of an already approved design, not a new protocol decision.

## Global constraints

- W = 4; installation-wide listener cap 512, configurable downward only; 30-second monotonic challenge deadline.
- Device persists d=k+1 and f=max(f,c) after host verification and before device proof. Host verifies device proof, locks, reloads state and current authority, then persists c=k+1 before completion.
- No unauthenticated counter advances, wrapping, lower generations, remote recovery, new cryptographic primitives, or hosted deployment.
- Persist with temporary write, file fsync, rename and directory fsync; any uncertain error aborts the next protocol message.
- Snapshot restoration requires explicit fail-closed operator ceremony, epoch/generation advancement and reapplication of later revocations.
- No publication before applicable full checks and Policy guard; protected delivery and exact merged-tree verification remain separate from local evidence.

## Review focus

- Stale concurrent attempts across endpoints/processes must never overwrite a newer floor or generation.
- A write error after rename may have committed: retries must use durable state and recovery rather than infer rollback.
- Lost completions must not exhaust the window; genuine-host-proof/device-proof drops exhaust exactly the accepted bounded window. The combined three device-proof losses plus a fourth committed attempt with lost completion is recorded on #1526 and awaits disposition.
- Pending handover retries must resend the same seed/generation and never expose a newly active generation before device acknowledgment.
- Malformed/missing state and restored snapshots must not silently regenerate authority or downgrade to v1.
