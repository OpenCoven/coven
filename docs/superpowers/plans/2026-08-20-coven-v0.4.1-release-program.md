# Coven v0.4.1 Release Program Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Release Coven v0.4.1 from one immutable, fully certified commit with clean branch state, reliable cross-platform gates, provider-owned setup for the three supported built-ins, and matching npm and GitHub publication.

**Architecture:** Treat `coven-v041` as a program of small, dependency-ordered Beads rather than one patch. Foundation, branch integrity, reliability, setup, and publication work land independently; then one exact `origin/main` SHA is frozen and all final evidence, the RC, the signed tag, npm packages, and GitHub Release attest that SHA. Rust owns setup policy and process boundaries, CI uses fake harnesses without credentials, and real authenticated certification is an operator-run local step.

**Tech Stack:** Rust stable, Cargo, Clap, existing Coven harness adapters and PTY/process supervision, Rust integration tests, Node.js 24, npm trusted publishing with GitHub Actions OIDC, GitHub Actions, Bash/PowerShell, Beads 1.2.2 schema v53, `gh`, and git signed tags.

## Program Rules

### Authoritative graph

The `coven-v041` epic and its 30 children are the authoritative task list.
Before claiming any bead, run:

```bash
bd dep cycles
bd ready
bd show coven-v041
bd show coven-v041-scope
```

Expected: no dependency cycle; the selected bead is ready; its acceptance
criteria and blockers match this plan. If Beads and this document differ, stop
that bead, update the design/plan through review, and follow Beads after the
correction lands.

### One bead, one worktree, one review boundary

Every code or documentation bead uses its own issue-keyed claim, branch,
worktree, commit series, and PR. Before editing:

```bash
coven claim status
gh pr list --state open --limit 100
git fetch origin main
```

Use the first executable bead as the concrete claim pattern:
`coven claim acquire bead-coven-v041-scope`, followed when needed by
`coven claim heartbeat bead-coven-v041-scope`. For later tasks, use the
explicit Bead ID printed in the task heading after the `bead-` claim prefix.
Do not release a claim until the PR merges or the work is explicitly stopped
and preserved.

Operational evidence beads such as freeze, certification, RC, tag, and
postflight do not manufacture source diffs. They record evidence in Beads and
the release system; if a source change is needed, reopen the appropriate
implementation bead and invalidate downstream evidence.

### PR readiness packet

Every PR states:

- Bead ID and exact acceptance criteria addressed;
- scope and explicit exclusions;
- risk and rollback or forward-recovery strategy;
- targeted test commands and results;
- full-gate results when required;
- security/privacy impact;
- documentation impact;
- evidence that the branch was based on current `origin/main`.

Use a conventional-commit subject and include:

```text
Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>
```

Create commits with `git commit -s` so the repository's DCO sign-off is also
present.

### Repository gates

Run the full repository gates for release-blocking Rust, workflow, packaging,
or cross-surface changes:

```bash
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace --locked
python3 scripts/check-secrets.py
python3 scripts/check-coven-privacy.py --staged
git diff --cached --check
```

For a TypeScript package that declares build and test scripts, also run those
commands from that package directory:

```bash
npm run build
npm test
```

Stage only the exact files named by the active bead before the staged privacy
check. Never stage unrelated files to make the privacy check pass.

### Release shell guards

Run every multi-command release guard block under Bash and begin it with:

```bash
set -euo pipefail
```

Do not run these blocks under `sh` or copy individual commands out of a guard.
The strict Bash mode makes failed comparisons, unset handoff values, and failed
pipeline stages stop the ceremony instead of allowing publication to continue.

### Product-code planning rule

Before implementation, every code-bearing bead must either point to an
approved focused design and implementation plan or add a small pair under
`docs/superpowers/specs/` and `docs/superpowers/plans/` in a docs-only PR.
The focused plan must name exact files, failing tests, minimal implementation,
targeted validation, and commit boundaries. This master plan coordinates those
patches; it does not turn the release into one mega-patch.
