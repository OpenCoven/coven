# Coven v0.4.1 Release Readiness Design

Bead: `coven-v041`

## Goal

Release Coven v0.4.1 from a clean, attributable repository state with reliable
cross-platform gates, first-class provider-owned setup for Codex, Claude Code,
and GitHub Copilot CLI, authenticated local certification, and consistent npm
and GitHub publication.

The release is complete only when one immutable commit has passed every
required gate, is represented by a signed annotated `v0.4.1` tag, publishes all
five npm packages with provenance, creates the matching GitHub Release with
four deterministic archives and `SHA256SUMS`, and passes postflight checks from
fresh consumer environments.

## Current Evidence

The release program begins from evidence, not an assumption that a green
default branch is release-ready:

- The tag-driven npm workflows for v0.3.0, v0.3.1, and v0.4.0 completed
  successfully and published through the current npm release path.
- GitHub Releases are missing for v0.3.0, v0.3.1, and v0.4.0 even though the
  tags and npm workflows exist. The latest listed GitHub Release is v0.2.5.
- A generated `npm/dist` tree was observed stamped as 0.2.4 while authoritative
  source package manifests intentionally remain at the `0.0.0` sentinel.
  Release-time tag stamping is intentional; stale generated output is not.
- PR 773 is polluted. Its approved duplicate tool-call-ID fix is commit
  `f61481446a3c`, while three later commits contain unrelated Bound design,
  planning, and implementation work.
- Four cave hardening commits remain to be landed or proven redundant:
  `b79713325bb5`, `040ad2fe4a8c`, `6ccbfc284247`, and `6b9b91614e12`.
- Known reliability evidence already exists in `coven-omf`, `coven-5ua`, and
  GitHub issue 751. These cover shared claim-state interference, a
  load-sensitive Windows detached-PTY timeout test, and a parallel
  memory-migration collision.
- Beads has been upgraded to 1.2.2 and migrated from schema v49 to v53. The
  completed `coven-v041-db` bead records recovery exports, clean integrity and
  cycle checks, and bounded query evidence.

These are release inputs. None may be dismissed as unrelated noise without an
explicit, evidence-backed disposition.

## Release Program Shape

`coven-v041` is the single release epic. Its 30 children form these ordered
lanes:

1. **Foundation:** Beads health, scope inventory, and the v0.4.0-to-candidate
   regression audit.
2. **Branch integrity:** reconstruct PR 773, preserve Bound outside the
   release, dispose the cave commits, and clean branches, worktrees, and claims.
3. **Reliability:** fix the known claim, PTY, and memory-migration flakes; add
   bounded stress coverage; then prove the frozen candidate on Linux, macOS,
   and Windows without success-by-rerun.
4. **Setup and certification:** lock the setup contract, implement shared
   orchestration and the three providers, add ephemeral verification,
   adversarial tests, user documentation, hermetic parity, and real local
   certification.
5. **Publication:** reconcile release history, automate GitHub Release assets,
   remove stale generated distribution state, verify npm preflight, and align
   the operator runbook.
6. **Candidate convergence:** freeze one exact `origin/main` SHA after all
   implementation, documentation, workflow, cleanup, audit, and stress work has
   landed.
7. **Frozen-SHA proof:** run reliability, parity, package smoke, and
   authenticated certification against that exact SHA.
8. **Release:** certify the RC, push the signed tag, verify npm and GitHub
   publication, and clean coordination state.

The Beads dependency graph is authoritative. `bd dep cycles`, `bd ready`, and
`bd show coven-v041` are release controls, not optional project-management
checks.

## Supported Built-ins

The exact built-in harness set for v0.4.1 is:

- Codex
- Claude Code
- GitHub Copilot CLI

No speculative harness adapter may enter the release critical path. Existing
opt-in adapter recipes remain separate from the built-in setup and
certification contract.

## Provider-Owned Setup Contract

### Public command

The public surface is:

```text
coven setup [codex|claude|copilot|all]
```

The default operation discovers the selected CLI, explains exactly which
provider-owned command Coven will launch, obtains explicit consent, and then
hands the terminal to that command.

The provider commands are fixed:

| Provider | Command |
| --- | --- |
| Codex | `codex login` |
| Claude Code | `claude auth login` |
| GitHub Copilot CLI | `copilot login` |

`all` processes the three built-ins in the order above and reports an
independent outcome for each. One provider's failure must not erase the other
providers' results.

### Missing installation

If a selected CLI is missing, Coven prints only official installation
guidance. It does not run an installer, download a binary, invoke a package
manager, or select an unofficial distribution channel. The result is
`not_installed`, distinct from an authentication failure.

### Consent and terminal ownership

Consent is required immediately before every provider launch. The prompt names
the executable and arguments. Declining consent produces `declined` and
launches nothing.

The child inherits stdin, stdout, and stderr. Coven does not proxy, scrape,
parse, log, or retain the provider's interactive authentication exchange. This
preserves provider prompts, browser/device flows, terminal control, and
accessibility behavior.

Interactive setup requires a TTY. Non-TTY invocation produces `non_tty` and
launches nothing; it must not hang waiting for input or silently reinterpret
the request as headless authentication.

### Credential boundary

Coven must never inspect or capture:

- tokens, cookies, API keys, or authorization codes;
- provider keychains or credential files;
- environment variables for provider credentials;
- account names, email addresses, organization membership, or subscription
  state;
- provider login output.

Coven may discover an executable on `PATH`, obtain its version, launch the
documented provider command after consent, observe process termination, and
classify the bounded result. Provider-owned credential storage remains opaque.

### Outcomes

The command reports per-provider outcomes from this closed set:

- `completed`
- `not_installed`
- `declined`
- `cancelled`
- `provider_failed`
- `non_tty`
- `verification_failed`

Cancellation must remain distinguishable from provider failure. A signal or
user-aborted provider process is `cancelled`; a normal non-zero provider exit
is `provider_failed`. The CLI exits zero only when every requested provider
completed the requested operation. Human output and JSON must retain the
per-provider distinctions.

### Optional verification

Login and verification are separate consent boundaries:

- `--verify` may run a minimal provider turn after setup.
- `--verify-only` skips login and runs only the certification probe.

Both modes must explain that they require network access and may incur provider
usage or cost. A second explicit consent is required before the turn.
Verification uses the existing harness adapter, ephemeral Coven state, and a
fixed minimal prompt whose only asserted property is the expected completed
event. It must not inspect credential storage to predict whether the turn will
succeed.

Verification output is reduced to:

- harness;
- locally resolved CLI version;
- platform;
- candidate commit;
- duration;
- exit class;
- completion boolean.

The report excludes prompts, provider output, tool output, account data,
tokens, terminal control sequences, and private paths. Human-readable failures
are sanitized by the same boundary.

## Doctor Boundary

`coven doctor` remains offline and hermetic:

- it launches no Codex, Claude Code, or GitHub Copilot CLI process;
- it performs no provider network request;
- it does not inspect provider tokens, keychains, credential files, or account
  data;
- it never claims that authentication or provider access is verified;
- it may report that a CLI is present or missing and point the user to
  `coven setup`.

Local diagnostic wording such as “configured” must remain advisory and must
include that a provider turn was not verified. Authenticated verification
belongs only to the explicitly consented setup verification path.

## Authenticated Certification

Real-provider certification is an operator-run local release ceremony. It is
not a CI job.

At the frozen SHA, an authorized operator uses three already authenticated
provider accounts and runs `--verify-only` for Codex, Claude Code, and GitHub
Copilot CLI. The operator retains only the redacted report defined above and
attests that all three produced the expected completed event.

Each command's redacted JSON report is saved to a separate local file. The
operator combines those three files with `jq` into
`release-evidence/v0.4.1-certification.json`, which records the frozen SHA and
only the approved result fields. The aggregate then passes the repository
secret and privacy/redaction checks. It must not contain raw model text,
provider output, account identity, tokens, terminal control sequences, or
private paths; the three intermediate files remain local and uncommitted.

CI receives no provider credentials. CI parity uses fake harness executables
and fixtures to exercise argv, TTY, persistence, cancellation, timeout,
redaction, and exit behavior. Passing fake-harness parity is necessary but
does not substitute for the operator's authenticated certification.

## Candidate Freeze and Evidence Invalidation

All implementation, documentation, workflow, branch-integrity, audit, cleanup,
and runbook work must land before freeze. The freeze records the exact
`origin/main` commit and requires a clean worktree. Its durable handoff is one
Bead note line in the exact form `freeze_sha=<40-hex-sha>`.

After freeze:

- every downstream evidence, RC, and tag task re-reads that note with
  `bd show coven-v041-freeze --json`, validates that exactly one 40-hex SHA is
  present, fetches `origin/main`, and requires both `origin/main` and the task
  worktree's `HEAD` to equal it;
- reliability evidence must name the frozen SHA;
- three-harness parity evidence must name the frozen SHA;
- four-target package-smoke evidence must name the frozen SHA;
- authenticated certification must name the frozen SHA;
- the RC commit must equal the frozen SHA;
- the `v0.4.1` tag target must equal the frozen SHA.

Any later commit entering the release reopens `coven-v041-freeze`. It also
invalidates and reopens reliability, parity, package-smoke, certification, RC,
and any evidence affected by the change. Evidence from “almost the same”
commit is not accepted. Shell state from another task, worktree, or machine is
not a valid SHA handoff.

## Publication Design

### npm

The existing tag-driven workflow remains the publication authority for:

- `@opencoven/cli`
- `@opencoven/cli-macos`
- `@opencoven/cli-macos-x64`
- `@opencoven/cli-linux-x64`
- `@opencoven/cli-windows`

Source manifests remain stamped `0.0.0`. The signed `v0.4.1` tag supplies
`0.4.1` to `scripts/publish-npm.mjs`. The four native packages publish first;
the universal wrapper publishes last. Publication uses npm trusted publishing
through GitHub Actions OIDC with provenance and no long-lived npm token.

Preflight must prove that all five package records and trusted publishers
exist, 0.4.1 is greater than `latest`, dry-run package contents are correct,
and the wrapper selects exactly the four native packages. The runbook may use
`npm trust list <package>` only with npm 11.16 or newer. On older npm, the
operator verifies each package's Trusted Publishers settings on npmjs.com and
records non-secret evidence for the same repository, workflow, and empty
environment checks.

### GitHub Release

Only after npm OIDC publication succeeds, the release workflow creates one
GitHub Release for `v0.4.1` with these exact deterministic asset names:

```text
coven-v0.4.1-macos-aarch64.tar.gz
coven-v0.4.1-macos-x64.tar.gz
coven-v0.4.1-linux-x64.tar.gz
coven-v0.4.1-windows-x64.zip
SHA256SUMS
```

Archive metadata, layout, executable modes, and ordering must be deterministic.
`SHA256SUMS` covers exactly the four archives. Missing, duplicated, or renamed
assets fail the workflow.

The absent v0.3.0, v0.3.1, and v0.4.0 GitHub Releases are an intentional
release-quality blocker. Each must be reconciled from verified tag, workflow,
npm, provenance, artifact, and reproducibility evidence before the v0.4.1
publication runbook is considered ready. If original archives are unavailable,
the release may be closed by reproducibly rebuilding from each immutable signed
tag, marking the assets and release notes explicitly as reconstructed,
recording workflow, tag, and commit provenance, and generating fresh
`SHA256SUMS`. Reconstructed assets must never claim byte identity with
unavailable originals.

Tags and published versions are immutable. A refused tag may be corrected only
before publication and under the runbook's safe procedure. A partial npm
publication is never overwritten or repaired under the same version; the fix
lands on `main` and publication moves forward to a new patch version.

## Failure Handling

- Missing CLIs produce official guidance and `not_installed`; Coven never
  installs them.
- Consent refusal produces `declined`; no provider launches.
- Non-TTY setup produces `non_tty`; no provider launches.
- Signals and user aborts produce `cancelled`; normal non-zero exits produce
  `provider_failed`.
- Timeouts terminate the provider process tree and produce a bounded failure.
- Verification failure does not rewrite setup as successful authentication.
- Redaction failure is fail-closed: no report is emitted or uploaded.
- A flaky release gate remains red until explained and fixed. A retry may
  diagnose a problem but cannot convert the original unexplained failure into
  release evidence.
- A platform outage or unavailable runner blocks that platform's evidence; it
  is not waived.
- A changed `origin/main` after freeze invalidates downstream evidence.
- A partial npm publish bumps forward; packages and tags are never overwritten.
- A GitHub Release asset mismatch fails publication and blocks postflight.

## Security and Privacy Boundaries

- Rust remains the authority layer for process launch, consent state, timeout,
  cancellation, result classification, and redaction.
- TypeScript and workflow code package and publish artifacts but do not make
  credential or setup-policy decisions.
- Provider authentication I/O flows directly between the provider CLI and the
  inherited terminal.
- CI uses fake harnesses and receives no real credentials.
- Certification records no account identity or provider output.
- Terminal control characters, secrets, and private paths are removed before
  any setup or certification result is persisted.
- Secret and staged-privacy checks remain mandatory. No release bead may weaken
  or allowlist around them.
- Release artifacts derive only from the signed frozen commit and pinned
  workflow dependencies.

## Testing Matrix

| Surface | Required proof |
| --- | --- |
| Setup CLI parsing | `codex`, `claude`, `copilot`, `all`, `--verify`, and `--verify-only`; invalid combinations fail |
| Provider discovery | present, missing, wrong executable, and version failure |
| Consent | accept, decline, cancellation before launch, and one consent per provider |
| TTY | inherited stdin/stdout/stderr; non-TTY refuses without launch or hang |
| Process lifecycle | success, provider failure, signal cancellation, timeout, descendant cleanup |
| Privacy | no token, account, environment, control-character, provider-output, or private-path leakage |
| Doctor | offline, hermetic, no provider launch, no authentication claim, setup pointer only |
| Fake parity | identical contract coverage for Codex, Claude Code, and GitHub Copilot CLI |
| Reliability | bounded repeated claim, migration, process, PTY, and short-socket-home tests |
| Platforms | Linux, macOS arm64, macOS x64, and Windows x64 package smoke; Linux/macOS/Windows Rust reliability |
| npm | five-package version graph, dry run, pack/install, wrapper-last ordering, OIDC, provenance, dist-tags |
| GitHub Release | deterministic four archives, exact names, executable layout, checksums, signed-tag ancestry |
| Real certification | three operator-run authenticated `--verify-only` checks at the frozen SHA |
| Documentation | onboarding and CLI documentation guards plus direct contract review |

The full repository gates remain:

```bash
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace --locked
python3 scripts/check-secrets.py
python3 scripts/check-coven-privacy.py --staged
```

Setup changes additionally require:

```bash
cargo test -p coven-cli --test setup_cli
cargo test -p coven-cli --test doctor_auth_boundary
cargo test -p coven-cli --test smoke -- --nocapture
```

## Release Completion Rules

v0.4.1 is complete only when all of the following are true:

1. `coven-v041-postflight` is closed and every other child of `coven-v041` is
   closed.
2. `bd dep cycles` reports no cycle and no release bead is blocked by an
   undispositioned dependency.
3. There is no open P0 or P1 release blocker, unexplained flaky gate, polluted
   release branch, stale claim, or dirty release worktree.
4. The frozen SHA, reliability SHA, parity SHA, package-smoke SHA,
   certification SHA, RC SHA, and tag target are identical.
5. The signed annotated tag is GitHub-verified and contained in `main`.
6. All five npm packages are 0.4.1 at `latest` with provenance.
7. The v0.4.1 GitHub Release contains exactly four archives plus
   `SHA256SUMS`, and checksum verification passes.
8. Fresh installation and onboarding smoke pass on every supported npm target.
9. Canonical documentation lists exactly Codex, Claude Code, and GitHub Copilot
   CLI as built-ins and states the setup, Doctor, verification, and credential
   boundaries accurately.
10. Release claims, merged branches, and stopped worktrees are cleaned only
    after evidence is preserved.
