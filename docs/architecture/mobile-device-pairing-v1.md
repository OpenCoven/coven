# OpenCoven Mobile Device Pairing Protocol v1

Status: Proposed implementation contract

Tracks: #784, #785, #786, #787, #788

## Purpose

This document defines the canonical trust and protocol contract for enrolling a mobile device into an OpenCoven trust domain, reconnecting it without repeating the enrollment ceremony, and authorizing sensitive actions with local user verification.

The protocol intentionally separates identity, authority, transport, and local authentication:

```text
trusted introduction
    -> authenticated key exchange
    -> device-bound credential
    -> scoped device grant
    -> encrypted session
    -> optional step-up authorization
```

A mobile device is a delegated principal. It is not the owner identity, a familiar identity, or an installation identity.

## Normative language

The key words MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, and MAY are to be interpreted as normative requirements.

## Principals and credentials

### Owner identity

The root of authority for a Coven trust domain. It issues, narrows, rotates, and revokes delegations. The owner private key MUST NOT be copied into a mobile client as part of pairing.

### Familiar identity

A portable agent identity. Revoking a device MUST NOT rotate, erase, or replace a familiar identity.

### Installation identity

A stable key identifying one Coven/Psyche installation. It authenticates the installation after first contact but is not advertised during ambient discovery.

### Device identity

A device-bound signing key generated by the mobile client. The private key SHOULD be non-exportable and hardware-protected when the platform supports it. The public identifier exposed to a trust domain MUST be pairwise or pseudonymous and MUST NOT be a hardware serial number, advertising identifier, or globally reused tracking identifier.

### Device grant

A signed authorization object binding a device public key to an audience, capabilities, restrictions, validity window, and revocation epoch. A grant is not sufficient by itself: authentication also requires proof of possession of the corresponding private key.

### Session keys

Ephemeral keys derived by the authenticated handshake. Session keys MUST provide forward secrecy and MUST be rotated for every new connection.

### Recovery credential

An optional passkey, recovery key, owner credential, or threshold of existing trusted devices. Recovery credentials MUST NOT silently become familiar identities or globally correlatable device identities.

## Cryptographic profile

Implementations MUST use reviewed cryptographic libraries and MUST NOT invent primitive constructions.

The v1 interoperability profile is:

- Hash: SHA-256
- Key agreement: X25519
- Signatures: Ed25519 for portable software identities; platform-native hardware keys MAY use P-256 with an explicitly encoded algorithm identifier
- AEAD: ChaCha20-Poly1305; AES-256-GCM MAY be negotiated where hardware policy requires it
- KDF: HKDF-SHA-256
- Serialization: deterministic CBOR
- Handshake: a reviewed Noise framework implementation using a pattern selected by the threat model and authenticated transcript requirements

Every signed or hashed protocol object MUST include a domain-separation string, protocol version, object type, and canonical serialization.

## Pairing offer

A pairing offer is a short-lived, single-use out-of-band introduction displayed as a QR code or copyable link.

```text
PairingOffer {
  version: 1
  session_id: bstr .size 32
  cave_ephemeral_key: COSE_Key
  rendezvous: [RendezvousHint]
  local_discovery_hint: bstr?
  requested_capabilities_hash: bstr .size 32
  expires_at: uint
}
```

The QR MUST NOT contain:

- permanent API or bearer tokens
- owner, familiar, installation, or device private keys
- biometric samples, templates, or hashes
- hardware serial numbers or advertising identifiers
- unnecessary familiar names, owner names, or account identifiers

The offer MUST expire within a bounded interval, MUST be single-use, and MUST become invalid after success, cancellation, or a bounded number of failed attempts.

A Universal Link/App Link MAY encode the offer in a URL fragment so ordinary HTTP request processing does not receive the offer payload.

## Enrollment state machine

```text
IDLE
  -> OFFER_CREATED
  -> RENDEZVOUS_CONNECTED
  -> HANDSHAKE_ESTABLISHED
  -> HUMAN_VERIFICATION_PENDING
  -> GRANT_PENDING
  -> ENROLLED
```

Terminal states are:

```text
ENROLLED | EXPIRED | CANCELLED | REJECTED | FAILED
```

Invalid transitions MUST fail closed. Pairing secrets MUST be destroyed on every terminal state.

### 1. Offer creation

The installation generates a cryptographically random session identifier and fresh ephemeral keypair, records an expiry, commits to the requested capability set, and displays the encoded offer.

### 2. Rendezvous

Both endpoints SHOULD establish outbound connections to a rendezvous service for the baseline transport. The service matches opaque session identifiers and forwards frames. It MUST NOT receive session plaintext or durable private keys.

A direct local connection MAY replace the relay after endpoint authentication. Discovery is not authentication.

### 3. Authenticated handshake

The endpoints perform an authenticated, forward-secret key exchange. The transcript MUST bind:

- protocol and cryptographic profile versions
- complete pairing offer digest
- installation ephemeral and static public keys
- device ephemeral and enrollment public keys
- requested capability digest
- fresh nonces from both peers
- selected transport and negotiated algorithms
- relay/rendezvous session identifier

Any mismatch MUST abort the enrollment.

### 4. Human endpoint verification

Both endpoints derive and display the same short authentication string from the handshake transcript. The installation MUST require explicit confirmation before it issues a durable device grant.

The short string is defense in depth and MUST NOT replace cryptographic transcript authentication.

### 5. Device enrollment request

The mobile client signs a canonical enrollment request containing the transcript hash, device public key, requested capabilities, nonce, expiry, and pairwise device identifier.

### 6. Grant issuance

The installation or owner authority issues a signed DeviceGrant. The grant MUST be no broader than the permissions displayed and approved during pairing.

## Device grant

```text
DeviceGrant {
  version: 1
  grant_id: bstr .size 16
  subject: DeviceKeyReference
  issuer: IdentityReference
  audience: TrustDomainReference
  capabilities: [Capability]
  restrictions: GrantRestrictions
  issued_at: uint
  not_before: uint
  expires_at: uint
  revocation_epoch: uint
  confirmation_key: DeviceKeyReference
  signature: COSE_Sign1
}
```

The subject and confirmation key MAY refer to the same key in v1. They remain separate fields so future delegation forms do not require changing the authorization model.

### Initial capability vocabulary

- `sessions.metadata.read`
- `conversations.read`
- `messages.send`
- `tools.request`
- `tools.approve`
- `secrets.read`
- `memory.familiar.read`
- `memory.familiar.write`
- `identity.admin`
- `devices.enroll`
- `devices.revoke`
- `identity.export`
- `memory.export`

Unknown capabilities MUST be rejected by default. Implementations MAY preserve unknown extension fields for forwarding but MUST NOT grant their authority without understanding them.

### Restrictions

A grant MAY restrict:

- familiar, project, workspace, or session selectors
- action classes
- assurance level
- transport or network conditions
- absolute expiry
- maximum idle duration
- approval frequency
- application or key attestation properties

## Authentication and reconnection

Returning devices authenticate with a fresh challenge and proof of possession of the device key. A display name, hostname, IP address, BLE identifier, push token, or relay session is never sufficient.

Every reconnection MUST:

1. validate the current grant signature, audience, validity window, and revocation epoch;
2. authenticate both endpoints;
3. derive fresh forward-secret session keys;
4. re-evaluate current policy and narrowed scopes;
5. reject stale resumption state that would restore revoked or removed authority.

Session resumption material MUST be sender-constrained or cryptographically bound to the device key. It MUST NOT be a reusable bearer token.

## Local discovery and direct transport

Local discovery SHOULD advertise only opaque, rotating identifiers. It MUST NOT expose stable owner, familiar, or device identifiers by default.

A client MAY attempt an authenticated direct LAN connection and fall back to an end-to-end encrypted relay connection. Changing transport MUST NOT change endpoint identity or authorization.

BLE MAY provide optional proximity evidence. Sensitive application traffic SHOULD use the established authenticated transport rather than BLE solely for convenience.

## Local user verification

Biometrics are local user verification, not network credentials.

```text
biometric / device-owner verification
    -> OS authorizes protected key operation
    -> device signs a fresh challenge or exact action digest
    -> Coven verifies signature and grant policy
```

Biometric samples, templates, and derived biometric hashes MUST never leave the platform biometric subsystem.

Implementations MUST distinguish these assurance levels:

1. `possession` — valid proof of device-key possession and grant
2. `recent_user_verification` — accepted local verification within policy window
3. `fresh_biometric` — biometric-only verification immediately before the operation, where supported
4. `step_up` — additional trusted device, recovery credential, owner credential, or threshold ceremony

A platform PIN/passcode fallback MUST NOT be silently represented as biometric-only assurance.

## Transaction authorization

Sensitive approvals MUST sign the exact canonical operation, not a generic boolean approval.

The authorization object MUST include:

- operation type
- material target and effect fields
- actor/device/grant references
- nonce
- issued-at and expiry
- current policy or request digest
- human-readable presentation digest

The mobile UI MUST render all material fields covered by the signature. Middleware MUST NOT be able to display one action while obtaining authorization for another.

## Revocation, rotation, and recovery

Revocation is evaluated through a signed revocation record, current revocation epoch, or both. A revoked device MUST fail on reconnect and MUST NOT regain access through stale resumption material.

Key rotation MUST create an auditable succession relationship and invalidate the superseded key according to policy.

Recovery MUST distinguish:

- regaining account/access capability
- enrolling a new installation or device
- rotating the owner identity
- rotating a familiar identity

These are separate operations and MUST NOT occur implicitly as one another.

Potential recovery factors include a passkey, recovery key, existing trusted device, N-of-M trusted devices, or the owner root credential. A compromised account or rendezvous service alone MUST NOT be able to mint device authority.

## Optional attestation

App and hardware attestation MAY increase assurance. It MUST be represented as a policy attribute, not as the canonical identity root.

Suggested values include:

- `verified_official_app`
- `verified_hardware_key`
- `unattested_device`

Self-built clients, development builds, alternative Android distributions, and self-hosted deployments remain valid participants subject to owner policy.

## Audit events

Implementations MUST emit structured, privacy-conscious audit events for:

- pairing offer created, expired, cancelled, and consumed
- enrollment requested, approved, rejected, and completed
- authentication success and failure
- step-up requested, approved, rejected, and expired
- grant issued, narrowed, rotated, expired, and revoked
- device key rotated
- recovery started and completed

Audit records MUST NOT include private keys, biometric material, raw recovery secrets, or decrypted application payloads.

## Required security tests

The implementation test suite MUST cover:

- replayed and expired offers
- duplicate offer consumption
- transcript substitution
- key and capability substitution
- MITM and wrong-peer pairing
- protocol and algorithm downgrade
- malformed and non-canonical CBOR
- relay reordering, duplication, truncation, and injection
- stolen grant without private key
- stale resumption after scope narrowing or revocation
- transaction presentation/signature mismatch
- unknown capability and restriction handling
- clock skew boundaries
- cross-Coven correlation checks
- cancellation and secret erasure on every terminal path

## Delivery sequence

1. Merge this protocol contract, schemas, threat model, and test vectors.
2. Implement the shared protocol library and conformance tests.
3. Implement TUI pairing and device-management commands.
4. Implement rendezvous relay and direct-transport abstraction.
5. Implement Pocket device-key storage and biometric authorization.
6. Implement returning-device reconnection and local discovery.
7. Implement recovery, trusted-device introduction, and optional attestation.

No client-specific implementation may broaden capabilities or weaken verification semantics relative to this contract.
